## Secure primitives do not automatically make a secure protocol

A **cryptographic primitive** supplies a defined function or security service under specific mathematical and operational assumptions. A **cryptographic protocol** combines messages, participants, state, keys, nonces, algorithms and verification steps to pursue higher-level objectives. A protocol's overall security depends on how these parts are selected, combined, bound to identities and contexts, and used over time.

An encryption primitive can hide a plaintext from parties lacking the key under its security assumptions. That does not alone establish that a message came from the claimed sender, was not replayed, was delivered to the intended recipient, or was generated by a trustworthy endpoint.

A message authentication code can help detect unauthorized changes under a shared-key security model. It does not by itself uniquely identify which of two parties who possess the same secret generated the message. A digital signature gives different origin-verification capabilities, but connecting a verification key to a real-world identity requires additional trust and identity evidence.

Security therefore emerges from **explicit composition constraints**, not simply from listing cryptographic algorithms in a design.

## Distinct security services and mechanisms

| Component | Primary modeled function | It does not prove by itself |
| --- | --- | --- |
| Symmetric encryption | Conceal protected plaintext under a shared key and defined assumptions | Endpoint identity, authorization or message freshness |
| Hash function | Compute a digest; may support collision/preimage resistance under security assumptions | Origin authentication of an arbitrary unkeyed message |
| Message authentication code (MAC) | Verify integrity and authenticity relative to a shared secret and message context | Publicly verifiable attribution to one unique signatory |
| Digital signature | Verify a signature relative to a verification key and signed message | That a certificate or key identifies the claimed human |
| Key agreement / KEM | Help parties establish or encapsulate shared secret material under a specified adversarial model | That parties' real-world identities have been authenticated |
| Authenticated encryption (AEAD) | Protect confidentiality and ciphertext integrity, with additional authenticated data | Replay prevention, recipient permission or complete endpoint security |
| Protocol key schedule | Derive context-separated keys from input secrets and transcript/context | Correct trust-anchor selection or protection of compromised clients |

These are service distinctions, not universal claims about all algorithms. Algorithm selection, parameters, implementation, key management, and attack models matter.

## Authenticated encryption with associated data

**Authenticated encryption with associated data (AEAD)** protects encrypted plaintext and also authenticates designated **associated data** without necessarily encrypting that associated data. Its abstraction involves a secret key, a nonce when required, plaintext and associated data, and produces ciphertext plus authentication information under algorithm-specific conventions.

The [IETF RFC 5116](https://www.rfc-editor.org/info/rfc5116/) defines an AEAD interface, while [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) specifies Galois/Counter Mode (GCM) and GMAC. Associated data is useful when a message header must remain readable for routing but must not be altered without detection, provided sender and receiver agree on which header bytes are authenticated and how they are encoded.

**Nonce management is a security obligation.** For common GCM and RFC 5116 nonce-based AEAD uses, encryptions under a particular key must meet the applicable uniqueness constraints. Nonce reuse under the same key can undermine important confidentiality or integrity guarantees. A nonce is not automatically secret, and uniqueness is not identical to unpredictability. Some alternative AEAD constructions offer different misuse-resistance properties; nonce rules cannot be generalized to every algorithm without reading its specification.

## Key establishment and identity binding

**Key establishment** lets participants obtain keying material under a chosen protocol. A **key-encapsulation mechanism (KEM)** can support establishing a shared secret through encapsulation and decapsulation, but a KEM alone does not generally prove the participants' identities.

NIST's [SP 800-227 (2025)](https://csrc.nist.gov/pubs/sp/800/227/final) gives definitions and guidance for KEM use. [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final) specifies ML-KEM for key encapsulation, while [FIPS 204](https://csrc.nist.gov/pubs/fips/204/final) and [FIPS 205](https://csrc.nist.gov/pubs/fips/205/final) specify distinct post-quantum **digital signature** families. These algorithms do not serve interchangeable purposes.

A protocol must define how to prevent an attacker from substituting a public key, replaying an old message, or binding a key to the wrong principal or session. Depending on the design, authentication might use certificates, pre-shared secrets, signed handshake messages, a verified public-key directory, or another explicitly specified mechanism.

**A shared secret is not proof that the peer is who the application believes it is** unless the protocol and trust assumptions establish that binding.

## Context, transcript and key separation

A sound protocol design typically distinguishes keys used for different purposes or directions. **Key derivation** can incorporate session context, labels, transcripts or roles so that keys intended for one use are not inadvertently reused for another. This is not merely a naming convention: the security argument must show why the derivation function and key material provide the required independence or separation.

**Handshake transcript authentication** can bind the negotiated parameters and exchanged messages to the established context. Without proper binding, parties might disagree about what they authenticated or what protection parameters they selected.

[TLS 1.3, RFC 9846 (July 2026)](https://www.rfc-editor.org/info/rfc9846/) is a useful *specific protocol example*: its handshake derives traffic keys using a key schedule and handshake transcript, and its record protection uses authenticated encryption. RFC 9846 **obsoletes RFC 8446 (2018)** while retaining TLS 1.3 and clarifying/tightening security requirements, including forbidding reuse of certain key-share values between connections. TLS is not a universal template whose named steps must be copied into every future protocol. TLS 1.3 **0-RTT early data does not provide inherent between-connection anti-replay guarantees**; the current RFC defines server-side mitigations with deployment constraints and requires applications to address replay-safe behavior. It is inaccurate to treat all TLS 1.3 data as having identical freshness or anti-replay properties.

## Replay and freshness

A valid cryptographic authentication tag may verify on a **message that was sent earlier**. Authentication of message contents is not synonymous with the claim that a message is fresh, unique or authorized to be acted upon again.

Protocol designs can address replay through counters, sequence numbers, challenge values, timestamps, stateful anti-replay windows or transaction identifiers, subject to clock reliability, wraparound, persistence, partitioning and other assumptions. A timestamp alone is not sufficient when parties have unsynchronized clocks or when a replay remains within an accepted time window.

**Worked example:** A client signs a request “transfer amount 5” and sends it to a server. The server verifies a valid signature. If an observer replays the identical signed request and the server has no adequate transaction-uniqueness or replay rule, signature verification may succeed again. The signature established a key-relative message relation; it did not guarantee that the transfer should happen twice.

This is a hypothetical logical scenario, not an implementation recipe or evidence that any deployed product is vulnerable.

## Composition counterexample: encryption without origin evidence

Imagine a system that encrypts and decrypts messages under a key but performs no message authentication. Under a model where ciphertexts can be replaced, the receiver may lack sufficient grounds to assert that a decrypted message was created by the expected sender or was unmodified. Exactly what attacks are possible depends on the encryption construction, error handling and channel assumptions; the word “encrypted” does not guarantee authenticated integrity.

Now imagine using AEAD with correct key and nonce management, then supplying the decryption result to an application that ignores the verified recipient, authorizing principal or transaction context. AEAD can authenticate selected bytes under the key, but the **application's authorization or replay decision** may still be incorrect.

The lesson is not that AEAD is unsafe. It is that **cryptographic correctness, protocol security and business authorization** have different proof obligations.

## Lifecycle, algorithm agility and quantum-resistant transitions

Keys are generated or established, stored, used, retired, rotated, archived, destroyed or potentially compromised according to their purposes. [NIST SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final) supplies key-management guidance. A secure protocol depends on key provenance and lifecycle, including whether revoked or compromised keys can still influence future sessions.

**Cryptographic agility** means designing and governing the ability to change algorithms, parameters, protocols and trust material without creating new unsafe downgrade opportunities or confusing compatibility with acceptance. Post-quantum migration is a significant example, but selecting an algorithm standardized in FIPS is not proof that a whole composed application or deployment is secure.

The working SF-09-07 subject owns broad key lifecycle and cryptographic failure concepts. This SF-09-09 pilot owns *composition and protocol-specific conditions* that span primitives.
